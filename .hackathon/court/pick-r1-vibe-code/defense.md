# Defense — R1 vibe-coded and vulnerable (N=5)

1. **Claim:** [V] AI-written code is insecure often enough to matter: Veracode's GenAI Code Security Report (Oct 2025 update page, as cited in the case) found risky security flaws in 45% of tests across more than 100 LLMs and four languages. Larger and newer models did not do better, so better models will not fix this on their own.
   **Why it matters to a real user:** A student who ships whatever Cursor or Copilot writes has close to a coin-flip chance of shipping a security flaw, and switching to a newer model will not change that.
2. **Claim:** [V] The team's top target, database access rules left off, is a documented and severe failure in AI-built apps. CVE-2025-48757 (GitHub advisory GHSA-773x-pxjg-gxgx, 30 May 2025, CVSS 9.3) covers missing Supabase row-level security in Lovable-generated sites. A researcher scan (mattpalmer.io, 29 May 2025) found inadequate row-level security in 170 of 1,645 Lovable showcase projects (about 10.3%), which leaked names, emails, API keys and payment status.
   **Why it matters to a real user:** People who use these apps had their personal and payment data exposed. The checker goes after this exact root cause rather than general code quality.
3. **Claim:** [V] Leaked keys get worse with AI assistance. GitGuardian's State of Secrets Sprawl 2026 (as cited in the case) reports that AI-assisted commits co-authored by Claude Code leak secrets at about twice the baseline rate on public GitHub, with about 28.6M new secrets found in public commits in 2025. This supports the team's "keys in frontend" pattern.
   **Why it matters to a real user:** A first-year student whose API key is pushed to a public repo or a frontend bundle can face abuse of the key and surprise bills before they even know what a secret is.
4. **Claim:** [T] The planned design suits the least-digital user and the CI operator. It checks a short list of specific patterns (access rules off, keys in frontend, routes without auth) and offers a one-click fix, so the user does not need to understand row-level security or injection to act on a finding. A "keys in frontend" check could also go beyond what a plain secret scanner like Gitleaks looks for. [AI] Because the check is rule-based rather than just a prompt to a hosted model, its findings can be repeated and checked, which the track rules require. It could run next to Semgrep, Gitleaks and pre-commit hooks without replacing them.
   **Why it matters to a real user:** A beginner gets a plain, fixable result instead of a wall of generic warnings, without changing tools or slowing down. That is the challenge's "without slowing the developer" requirement.
5. **Claim:** [T] One complete, honest journey can be built in about 21 hours. The hypothesis is narrow (three patterns), the baseline is fixed (Semgrep plus Gitleaks), the test set is seeded AI-built apps the team owns (which also follows the "test only own code" rule), and there are four roles (backend/DB, UI, AI/core logic, integrations/testing) to cover scanner, fix, interface and evaluation. [?] Two points are untested: whether free scanners already catch these patterns, and whether Indian student developers would run an extra check. The head-to-head comparison and failure analysis are designed to answer the first.
   **Why it matters to a real user:** Developers and judges get measured evidence of whether the tool finds more real issues with fewer false alarms than the free tools they already have, not just a claim.
