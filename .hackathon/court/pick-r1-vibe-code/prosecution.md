# Prosecution — R1 vibe-coded and vulnerable (N=5)

1. **Claim:** [V] Lovable, the platform that produced CVE-2025-48757, now does the checker's core job itself. It scans RLS before every publish (built on Supabase's Security Advisor), blocks hard-coded private API keys (it says about 1,200 times a day), and has an AI reviewer that flags hard-coded secrets, unprotected endpoints and auth flaws. Source: [Lovable blog "secure vibe coding"](https://lovable.dev/blog/secure-vibe-coding), posted 9 June 2025, opened 2026-11-20.
   **Why it matters to a real user:** A Lovable/Supabase student already gets free checks for the team's three headline patterns (RLS off, keys in the frontend, routes without auth) at the moment they hit publish, so a separate tool mostly adds a second warning for the same thing.
2. **Claim:** [T] The case lists "whether Indian student devs would run an extra check before shipping" as [?], and KEY ASSUMPTIONS are "none recorded yet". There is no user evidence that the target developer would adopt a new tool or step.
   **Why it matters to a real user:** The first-year student who doesn't know what RLS or injection is won't install or run a scanner they never thought they needed. The people most at risk are the ones least likely to use it.
3. **Claim:** [T] The case's own root cause is "nobody reviews it". The proposed fix is another automated scanner on top of free Semgrep, Gitleaks and GitHub secret scanning, which the case itself says are free and widely recommended. That case claim is only [AI], from a search snippet nobody opened.
   **Why it matters to a real user:** A developer who already ignores free scanner output gets one more list of alerts. The gap is in understanding and review habits, not in having enough scanners, so the end users of the shipped apps stay exposed.
4. **Claim:** [AI] Config checks like Supabase's Security Advisor (and Lovable's scan built on it) only check structure: is RLS on, does a policy exist. They don't check whether the policy actually blocks access, and a `using (true)` policy turns the warning off while leaking everything. Source: [guardlayer.io](https://www.guardlayer.io/blog/supabase-security-advisor), a vendor blog seen in search results 2026-11-20 but not opened. (The prosecution labelled this [V]; relabelled [AI] by the clerk because the page was not opened.) A static "RLS off" detector with a one-click fix risks the same trap.
   **Why it matters to a real user:** A beginner who clicks "fix" and gets a green check believes the app is safe while user names, emails and payment data can still be read. That is worse than no tool, because it gives false confidence.
5. **Claim:** [T] The hypothesis will be tested only on "a seeded set of AI-built apps the team owns", in about 21 hours, against a Semgrep+Gitleaks baseline. The track rule allows testing only your own code. [AI] Whoever planted the flaws decides what counts as a "real issue", so the comparison is built to favour the team's checker.
   **Why it matters to a real user:** Beating generic tools on the team's own planted bugs says nothing about whether the tool catches the varied, messy flaws in a real student's Cursor or Copilot app, or how many false alarms that student would get.
