# Plan 05-01: Payout Synchronization Hardening & Idempotency

## Objectives
Harden payout synchronization triggers in PostgreSQL to eliminate concurrency lost updates and reassignment deadlocks, and implement end-to-end client-side transaction idempotency to prevent duplicate financial records.

## Tasks

### Task 0: Database Migration (`20261121000100_harden_payout_sync.sql`)
- Add `PERFORM ... FOR NO KEY UPDATE` row locking in `public.sync_payout_received(p_payout uuid)`.
- Recalculate `received_amount` from `SUM(amount)` across all linked income transactions.
- Enforce status lifecycle: settled on >= 100%, partial on > 0%, scheduled on 0%, preserve cancelled/estimated/unearned.
- Order locks in `public.transactions_sync_payout()` by canonical ascending UUID to prevent cross-update deadlocks.

### Task 1: Client-Side Idempotency
- Update `NewTransaction` in `frontend/src/types/contracts.ts` with `id?: string`.
- Update `addTransaction` in `frontend/src/services/data.ts` to generate and persist `t.id` for retries.
- Update `receivePayout` in `data.ts` and `usePayouts.ts` with `idempotencyId`.
- Retain submission UUIDs in `AddTransactionPage.tsx` and `PayoutsPage.tsx` across retries.

### Task 2: PGlite Comprehensive Regression Suite
- Create `backend/scripts/test-payout-sync.mjs` verifying:
  - Partial receipt
  - Full settlement
  - Multiple linked receipts
  - Amount recalculation
  - Transaction deletion & status restoration
  - Payout reassignment
  - Duplicate UUID rejection via primary key
  - Direct edit rejection via guard trigger

### Task 3: Real Multi-Connection PostgreSQL Concurrency Test
- Create `backend/scripts/test-concurrency-postgres.sh` testing:
  - 10 simultaneous parallel client connections inserting against the same payout.
  - Simultaneous cross-reassignment testing deadlock freedom.
