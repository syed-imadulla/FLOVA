# Plan 05-02: Idempotent Retry UX Fix in `addTransaction`

## Objectives
Enhance `addTransaction()` in `frontend/src/services/data.ts` to recognize when a transaction insert fails with PostgreSQL unique constraint violation `23505` on `transactions_pkey`. If an existing transaction with the same UUID is found for the authenticated user and matches the financial payload, return the existing transaction as a successful idempotent retry. If fields conflict, throw an explicit conflict error; if the row is inaccessible or another constraint failed, propagate the original error.

## Tasks

### Task 0: Implement Idempotent Retry in `addTransaction`
- Inspect `res.error` for code `23505` and `transactions_pkey`.
- Query existing transaction row via authenticated client (`supabase.from("transactions").select("*").eq("id", t.id).maybeSingle()`).
- Verify financial fields (`type`, `amount`, `ownership`, `expense_type`, `payout_id`).
- Return existing transaction on match.
- Throw explicit conflict error on mismatch.
- Fall back to standard error propagation if not found or on other errors.

### Task 1: Add Comprehensive Regression Tests
- Create test suite covering all 7 scenarios (A through G):
  - A: Normal transaction insertion
  - B: First insert succeeds
  - C: Duplicate primary-key retry with matching payload returns success
  - D: Duplicate UUID with different financial data returns conflict error
  - E: Duplicate UUID with no existing visible row (RLS isolation) propagates error
  - F: Other unique constraint violation is not treated as idempotent retry
  - G: Payout receipt retry benefits without duplicating records
